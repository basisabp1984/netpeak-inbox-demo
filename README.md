# Inbox Classifier — демо-вітрина

Веб-інтерфейс до [класифікатора вхідних запитів](https://github.com/basisabp1984/netpeak-inbox-classifier).
Показує, що саме LLM витягла з кожного запиту — поруч із вихідним текстом.

**Живе демо:** https://netpeak.radai-1984.dev

---

## Навіщо це окремо

Тестове завдання просило скрипт: CSV → `output.json` + звіт. Це й лежить в
основному репозиторії, і саме воно здається на перевірку.

Ця вітрина — **окремий шар поверх готового результату**. Вона нічого не
класифікує і не викликає LLM: читає `output.json`, який виробив пайплайн.
Межа навмисна — основний репозиторій лишається самостійним CLI і не набуває
залежності від вебу.

Інтерфейс показує інженерні рішення, а не ховає їх:

- **дві колонки** — ліворуч вихідний запит, праворуч розбір моделі; видно,
  на чому саме ґрунтується класифікація;
- **збійні записи видно** — картка з `status="failed"`, текстом помилки
  валідації та **сирою відповіддю моделі**. Це доказ, що валідація працює,
  а запис не втрачається;
- **низька впевненість підсвічена** — `confidence < 0.6` окремим фільтром,
  як кандидати на перевірку людиною;
- **ймовірні дублі** — REQ-013 позначений як схожий на REQ-001.

## Запуск

```bash
docker compose up -d --build
# відкрити http://localhost:8011
```

Або без Docker:

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8011
```

Тести:

```bash
python -m pytest tests/ -q      # 38 тестів
```

## Архітектура

```
seed/output.json      результат прогону пайплайну (вхідні дані вітрини)
      ↓ startup, ідемпотентно
SQLite (data/demo.db) runs + items, індекси по category/priority/status
      ↓
FastAPI (app/)        /api/stats, /api/items, /api/runs
      ↓
web/                  ванільний JS без збірки
```

### Чому SQLite, а не Postgres

Вітрина читає дані й майже не пише, працює в одному контейнері, обсяг — сотні
записів. Postgres додав би другий контейнер, мережу, паролі та бекапи, не
вирішивши жодної наявної проблеми. Простіше перед складнішим; схема сумісна,
міграція при зростанні — заміна URL підключення.

### Що дає база порівняно з читанням файла

- **Ідемпотентність** — повторний імпорт того самого прогону не плодить дублі
  (`run_key` з метаданих). Перезапуск контейнера не ламає дані.
- **Історія прогонів** — таблиця `runs`; видно, як змінювалась класифікація
  між запусками й версіями промпту.
- **Фільтрація в SQL** — на 19 записах різниці немає, але це те, заради чого
  база й потрібна, коли записів десятки тисяч.

### API

| Endpoint | Призначення |
|---|---|
| `GET /api/health` | стан сервісу |
| `GET /api/runs` | історія прогонів |
| `GET /api/stats` | агрегати (ті самі цифри, що в `report.md`) |
| `GET /api/items` | записи; фільтри `category`, `priority`, `status`, `needs_clarification`, `search` |
| `GET /api/items/{id}` | один запит |
| `GET /api/docs` | Swagger |

## Безпека

Демо публічне, тому після код-рев'ю додано базовий захист.

**Токен доступу.** Змінна `DEMO_ACCESS_TOKEN` вмикає перевірку: без валідного
токена сторінка й API повертають 401. Токен приймається з посилання (`?k=…`),
з cookie або із заголовка `Authorization: Bearer …`; отриманий із посилання
закріплюється в httpOnly-cookie, щоб не тягнути його в кожному URL і не
світити в `Referer`. Порівняння — `hmac.compare_digest` (стале в часі: звичайне
`==` виходить на першому розбіжному символі, і токен підбирається посимвольно
за часом відповіді).

Якщо змінна не задана — доступ відкритий. Це навмисно: локально й для
перевіряючого зайвий бар'єр не потрібен.

> Це **не автентифікація користувачів**. Спільний секрет відповідає на питання
> «ця людина отримала посилання від власника», а не «хто саме ця людина».
> Для демо з тестовими даними цього досить; для реального інбоксу потрібні
> облікові записи й ролі.

**Що ще закрито після рев'ю:**

- **LIKE-ін'єкція.** `%` і `_` у полі пошуку працювали як wildcard —
  запит `?search=%` повертав **усі** записи в обхід наміру фільтра. Тепер
  екрануються з `ESCAPE`.
- **Стеля на видачу.** `limit` (за замовчуванням 200, максимум 1000) і `offset`:
  відкритий ендпоінт без обмеження — спосіб навантажити сервіс одним запитом.
- **Валідація значень.** `category` / `priority` / `status` — тепер `Enum`:
  сміття дає 422 з переліком допустимих значень, а не 200 із порожнім списком,
  який неможливо відрізнити від «нічого не знайдено».
- **Заголовки.** CSP (`default-src 'self'`, без `unsafe-inline`), `X-Frame-Options: DENY`,
  `nosniff`, `Referrer-Policy: no-referrer`.

SQL-ін'єкції не проходили й до рев'ю — усі параметри зв'язані, — але тести на них
тепер є явні.

## Обмеження

- **Дані статичні.** Вітрина показує збережений прогін; кнопки «перекласифікувати»
  немає навмисно — це вимагало б ключа LLM на публічному сервері.
- **Немає автентифікації.** Демо публічне й містить лише тестові дані із завдання.
  Для реального інбоксу знадобився б доступ за токеном.
- **Одна демонстраційна збійна запись** (REQ-019) додана до сиду штучно: живий
  прогін дав 18/18 успішних, і без неї не було б видно, як інтерфейс показує
  роботу валідації. У `raw_llm_output` — правдоподібна невалідна відповідь моделі.
- **Фронтенд без збірки.** Один екран, ванільний JS; фреймворк тут був би
  складним замість простого.
